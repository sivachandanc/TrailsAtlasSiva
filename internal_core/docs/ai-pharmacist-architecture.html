TRIAL ATLAS · ELIGIBILITY BUILDER · STEP 3

AI Pharmacist Architecture

How step 3 turns a trial's free-text eligibility criteria into checked filters on claims data: a LangGraph agent on Claude Opus 5.5 reads the text and looks up real codes and drugs, then plain code verifies everything it said before any of it becomes SQL.

The idea in plain words

A trial's eligibility criteria are written for doctors: “diagnosed with gestational diabetes during this pregnancy, not pre-existing diabetes, no gastric bypass, able to give consent”. Our member data is claims: diagnosis codes with dates, and the last date each drug was filled. Step 3 translates one into the other.

It works in two halves. An AI does the reading. Claude, told to act like a clinical pharmacist and coder, splits the criteria into single rules and, for each one, looks up the real ICD-10-CM codes or drugs and says how recent they must be. It isn't allowed to remember codes; it must find them with lookup tools. Plain code does the checking. Every quote must really be in the criteria, every code must exist, every drug must resolve to NDCs, and only then is SQL written. Anything claims can't answer (lab values, language, consent) is kept and shown as “needs review”, never guessed.

Nothing about members ever goes to the AI. It sees the trial's public text and the names of our tables, nothing more.

Example: the gestational diabetes trial (NCT05909046), run live on 14 Oct 2026
  • “Diagnosed with GDM during pregnancy” became must have O24.4, dated in the last 365 days. “During pregnancy” is approximated as the last year and marked for a reviewer to confirm.
  • “(NOT pregestational diabetes)” became two must-not-have rules: O24.0, O24.1, O24.3, O24.8 in the last year and E10, E11, E13 dated at least a year ago, i.e. diabetes before the pregnancy.
  • “History of gastric bypass” became must not have Z98.84, O99.84 or K95, any time.
  • Glucose test results, language, consent and “care at OSU” went to needs review, each with a reason.

After the agent submits: what gets verified

How to read it

No AI from here on. Read the top row left to right: each submitted rule passes through four checks in order, then the bottom row turns the survivors into SQL and the final result. Think of the agent's answer as a draft and this row as the editor: a made-up code is struck out, a quote that isn't in the trial is flagged, and only rules that pass everything are applied to members.

Time windows, explained

Most criteria say when something must have happened: “in the past 3 months”, “diagnosed at least 6 months ago”, “12 to 24 months postpartum”, “during this pregnancy”. Every one of these is stored the same way, as a range of days counted back from today: max_days_ago (no older than) and min_days_ago (no newer than). Either end can be open. The agent only describes the range; plain code turns it into dates, so the AI never does date arithmetic.

How the filter uses a window
  • Diagnoses: the member has a matching code dated inside the range. Every diagnosis date is kept, so all three shapes work. “At least 6 months ago” means some matching code is older than 180 days, so the condition has existed that long.
  • Medications: only the last fill is stored, so only “no older than” works: “taking metformin now” means the last fill is in the last 90 days. A “no newer than” limit on a drug means a duration or start date (“stable dose for 3 months”), which can't be checked, so it goes to review.
  • Events: when the criteria anchor timing to an event, the agent uses the standard table below if the event has a known length. Otherwise (“since surgery”) it leaves the window open and the rule goes to review.
Event in the criteriaStandard windowWhy
“currently taking”, “current”, “active”, “at screening / enrollment / baseline”last 90 days90 days is the longest common fill, so an active prescription or condition shows up
“within N weeks before screening / randomization / first dose”last N daysThe study visit is treated as today
“during this / the current / the index pregnancy”last 365 days40 weeks of pregnancy plus the first months after delivery
“postpartum”, “N to M months after delivery”a delivery code (Z37, O80…) in the stated range; “immediately postpartum” = last 30 daysThe delivery itself is coded
“current hospitalization / admission”last 30 daysMost stays are shorter than a month
“since surgery”, “since diagnosis”, “during the study”none: needs reviewNo fixed length, so any window would be a guess

The table is the same for every trial and lives in one place in the code (EVENT_APPROXIMATIONS in prompts.py). The agent may not invent other approximations. In a check of the 873 diabetes trials in the sandbox, about 29% mention “at screening / enrollment / baseline”, 16% “currently taking”, 7% pregnancy timing and roughly 2–4% a range, so this covers a large share of timing language. Many “at screening” lines are about lab values, though, and those stay in review either way.

A run, start to finish

  1. The coordinator clicks “Build with AI pharmacist”.The page POSTs to /api/trials/{id}/filters/criteria/run and starts reading a server-sent event stream.
  2. The backend checks it can run.The trial exists, has criteria text, isn't already being built (so no one pays twice), and an Anthropic key is set.
  3. It builds the context.The criteria text (the only source of rules); background that helps read it (official title, brief summary, interventions and arms, conditions, study population); step 1's ICD prefixes and step 2's age and sex rules, so the agent doesn't redo them. The system prompt also describes the member tables, so the agent knows what claims can check.
  4. The agent works through the criteria.Each Claude turn either writes a short progress note, asks for lookups (often several at once), or submits. Every lookup and its result streams to the page as it happens.
  5. It submits every rule in one call.The arguments are validated against the schema; anything malformed goes back to the model to fix.
  6. Plain code verifies and builds the filter.Quotes, codes and drugs are checked, drugs are expanded to NDCs, each rule is grouped, and SQL is written per rule and for the whole step.
  7. The result is shown and kept for a day.Reopening step 3 reads it from memory instead of paying for another run.

What the model gets, and what it must return

System prompt (cached)

Role: clinical pharmacist and certified coder for a health plan. The member tables and columns above, and what they can and can't answer (every diagnosis date; only the last fill per drug). How to split criteria into atomic must-have / must-not-have rules, find codes and drugs only through tools, describe time windows as a range of days without computing dates, use only the standard event approximations, keep non-codable rules with a reason, respect steps 1–2, write a one or two sentence progress update before each round of lookups (shown live in the activity feed), and finish with one submit_criteria call.

User message

Trial ID and title; what steps 1 and 2 already cover; background labelled “not a source of rules” (official title, conditions, brief summary up to 3,000 characters, interventions with other names and descriptions, arms with what each receives, study population); then the criteria text verbatim between <<< and >>>, marked as the only source of rules.

SQL it writes

-- diagnosis rule, must_have, any time
member_id IN (
  SELECT member_id FROM member_diagnoses
  WHERE code_system = 'ICD10CM'
    AND (icd_code LIKE 'O2411%')
)
-- medication rule, must_not_have, 90 days
member_id NOT IN (
  SELECT p.member_id FROM member_prescriptions p
  JOIN ndc_lookup n ON n.ndc = p.ndc
  WHERE (n.atc_class LIKE 'A10BK%')
    AND p.last_fill_date >= DATE '2026-07-16'
)
-- diagnosis rule, 12–24 months ago
member_id IN (
  SELECT member_id FROM member_diagnoses
  WHERE code_system = 'ICD10CM'
    AND (icd_code LIKE 'Z37%' OR icd_code LIKE 'O80%')
    AND diagnosis_date >= DATE '2024-10-14'
    AND diagnosis_date <= DATE '2025-10-14'
)

The step's SQL joins every “checked from claims” rule with AND under SELECT member_id FROM members. Codes are stored without dots, so O24.11 becomes the prefix O2411%. ndc_lookup is the planned RxNorm reference table (ndc, ingredient_rxcui, atc_class); the page also shows the live NDC count and samples per drug.

How it's guarded

The background sits under a heading that says it isn't a source of rules, the criteria are marked as the only source, the system prompt repeats it, and every rule's quote must be found in the criteria text or it's flagged. Glossary

ICD-10-CM
US diagnosis codes on medical claims, e.g. O24.4 gestational diabetes. Stored without the dot; a code covers its more specific codes.
NDC
National Drug Code: one per packaged product, on every pharmacy claim. A single drug has hundreds.
RxNorm, RxCUI
NLM's drug vocabulary and its IDs. Links brand names, ingredients and NDCs.
ATC class
A drug class code, e.g. A10BK for SGLT2 inhibitors. Lets one rule cover a whole class.
UMLS
NLM's service that links medical vocabularies; used here to search and check ICD-10-CM codes.
LangGraph
The library that runs the agent's loop: Claude's turn, the lookups, the hand-off.
SSE
Server-sent events: how the page receives the live activity feed while the agent works.
Codable
A rule claims data can answer, so it can become SQL.

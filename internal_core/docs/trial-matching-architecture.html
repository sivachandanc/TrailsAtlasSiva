Trial Matching Architecture

How one ClinicalTrials.gov trial is turned into filters and run against the predefined member dataset. Cheap SQL filters first, an LLM only for the criteria codes can't express, and people for whatever is left.

How one trial is processed

  1. Fetch the trial BuiltPull trials with at least one US site from the ClinicalTrials.gov API (AREA[LocationCountry]"United States"), keep only the fields we need, flatten them and store them in studies. A re-run replaces that search's rows. make fetch · explore_ctgov.py
  2. Build the predefined filters ICD built · age, sex plannedICD: for each MeSH ID + term pair keep the CUIs both lookups return, and search UMLS for each sponsor condition text. Map every CUI to ICD-10-CM, remove dots, cut to the first 3 characters (R and Z codes kept whole) and save each code with its source to trial_icd_codes. Age and sex parsing is next. make trial-icd NCT=… · trial_icd.py
  3. Apply them in SQL Needs member dataAge and sex against members, then the ICD prefilter: keep members with any ICD-10-CM code starting with one of the trial's prefixes (OR). A trial with no prefixes skips this step. The query is written (COHORT_SQL) and was tested on sample rows only.
  4. Ask the LLM for the remaining criteria PlannedSend the inclusion and exclusion text, the filters already applied, the data dictionary and today's date. It returns structured criteria as JSON, not SQL.
  5. Validate and compile PlannedCheck every ICD code against the reference table, and turn ingredients or ATC classes into NDCs through RxNorm. A fixed template per criterion type produces the SQL.
  6. Shortlist and review PlannedEach candidate gets met, not met or unknown per criterion. Unknowns and non-codable criteria go to a coordinator.

LLM contract

Inputs

Inclusion and exclusion text, the filters already applied (age, sex, ICD codes), the data dictionary with table and column descriptions, and today's date for time windows.

Output

Structured criteria in a fixed JSON format. Each one keeps the sentence it came from, so a coordinator can see why a member matched.

Never

Member rows, NDC numbers or raw SQL. Codes are checked against reference tables; drugs come back as ingredients or ATC classes.

{
  "criteria": [
    { "id": "inc_1", "kind": "inclusion", "type": "diagnosis",
      "icd10cm_prefixes": ["O2401", "O2411", "O2431", "O2481"],
      "window": { "relative_to": "today", "within_days": 270 },
      "source_text": "Women with pre-existing diabetes..." },
    { "id": "inc_2", "kind": "inclusion", "type": "medication",
      "ingredients": ["insulin", "metformin"],
      "atc_classes": ["A10A", "A10BA"],
      "source_text": "..." },
    { "id": "exc_1", "kind": "exclusion", "type": "not_codable",
      "reason": "investigator judgment",
      "source_text": "severe diseases that could bias BP..." }
  ]
}

Member data reaches an LLM only if step 5 ever uses one on the shortlist. Before that, a vendor agreement covering health data (a HIPAA BAA in the US) and minimum-necessary data must be in place.

Checked on a real trial

NCT05909046, a postpartum diabetes screening trial at Ohio State University, built the filter E11% OR O24% OR R7303% in about 2 seconds.

What worked

  • The target patients' codes (gestational diabetes at and after delivery, O24.42x, O24.43x) are all inside O24%. Exact matching on the mapped codes would have missed O24.42x.
  • MeSH and condition text agreed on O24, and MeSH supplied E11 where the sponsor's “Type2diabetes” matched nothing.
  • Prediabetes stayed R7303% instead of widening to all of R73.

What it showed

  • The conditions describe the study's topic, not who can join: E11% and pre-existing diabetes let in people the trial excludes. The prefilter loses no one but narrows little; step 3 has to do the narrowing.
  • There's no time check: a gestational diabetes code from years ago passes.
  • Glucose test results, language and “receiving care at OSU” can't come from claims.
  • “Pregnancy, High Risk” has no ICD-10-CM link in UMLS, although O09 exists.

Open questions for review

  • Age as of when? Today, or the member's expected enrollment date. Pick one and use it everywhere.
  • LLM-added codes. MeSH and condition text still miss codes (High-Risk Pregnancy → O09). How far should the LLM add codes on top, checked against icd10cm_codes?
  • Lookback windows. Default history to require when a criterion gives no time window, and how coverage gaps count.
  • Trials with US and non-US sites. About 1 in 5 stored trials also have sites abroad. When matching by location, only the US sites should count.
  • All trials at once. ICD lists are built one trial per run (~0.7 s each). A batch mode that looks up each distinct MeSH pair and condition text once would need ~3,000 UMLS calls for all 2,049 trials instead of ~17,000.
  • Reference data refresh. How often to rebuild ndc_lookup from RxNorm and the ICD-10-CM table (yearly release in October).
  • LLM on member records. Do we want it in step 5 at all, or keep the LLM strictly on the trial side?
